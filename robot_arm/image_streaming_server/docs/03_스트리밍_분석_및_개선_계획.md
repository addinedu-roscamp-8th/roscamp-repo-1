# video_feed 멈춤·느림 현상 분석 및 개선 계획

## 1. 현재 구조 요약

- **Flask 웹캠 서버** (`flask_webcam_server.py`)
  - 백그라운드 스레드 1개: 카메라에서 최대 30fps로 읽어 `_latest_frame` 갱신
  - `/video_feed`: MJPEG 스트림 — 요청마다 **별도 스레드**에서 `generate()` 무한 루프
  - 루프마다: `_get_latest_frame()` → `cv2.imencode(".jpg", frame)` → yield
  - `/snapshot`: AI 서버용 단일 이미지 다운로드
- **소비 측**
  - 브라우저: `<img src="/video_feed">` 로 MJPEG 재생
  - AI 서버: `source_fetcher.py` 에서 `requests.get(url, stream=True)` 로 `/video_feed` 파싱 후 YOLO 등 분석

---

## 2. video_feed 멈춤 현상 원인 분석

### 2.1 클라이언트당 인코딩 (가장 유력)

- `/video_feed` 접속자 **1명당** 스레드 1개가 돌면서 **매 프레임마다** `cv2.imencode()` 실행.
- 접속자가 브라우저 1개 + AI 서버 1개면, 같은 한 프레임에 대해 **인코딩이 2번** 발생.
- 라즈베리 파이에서 JPEG 인코딩은 CPU 부담이 크므로:
  - 인코딩이 실질 FPS를 10 이하로 떨어뜨림 → 화면이 끊기거나 멈춘 것처럼 보임.
  - 여러 스레드가 동시에 `imencode` 하면 GIL·CPU 경합으로 더 느려짐.

### 2.2 클라이언트 끊김 미감지

- `generate()` 가 `while True` 로만 동작하고, **클라이언트 연결 종료를 검사하지 않음**.
- 브라우저 탭을 닫거나 AI 서버가 타임아웃으로 끊어도, 서버 스레드는 계속 `imencode` 후 전송 시도.
- TCP 버퍼가 찬 경우 해당 스레드는 블로킹되고, 그만큼 워커 스레드가 묶여 전체 응답이 지연되거나 "멈춤"처럼 보일 수 있음.

### 2.3 카메라 읽기 실패 시 갱신 중단

- `_camera_loop` 에서 `ret, frame = _cap.read()` 가 실패하면 `_latest_frame` 이 갱신되지 않음.
- 그동안 `/video_feed` 는 **마지막으로 성공한 같은 프레임**만 계속 보냄 → 화면이 완전히 멈춘 것처럼 보임.

### 2.4 Flask 개발 서버 한계

- `threaded=True` 로 요청당 1 스레드. 장시간 스트리밍 연결이 여러 개면 스레드가 모두 스트리밍에 묶일 수 있음.
- 스트리밍 응답 버퍼링으로 인해, yield 한 데이터가 곧바로 클라이언트로 나가지 않고 쌓였다가 한꺼번에 나갈 수 있어 끊김/멈춤처럼 보일 수 있음.

### 2.5 기존 "너무 느리다" 이슈와의 관계

- 위와 동일한 구조 때문: **프레임당 인코딩 횟수 = 접속 클라이언트 수**.
- Pi CPU에서 그만큼 인코딩을 반복하므로 FPS 저하·지연이 발생했을 가능성이 큼.

## 3. 해결 방향 (종합)

목표:

1. **video_feed 멈춤 제거**: 끊김·같은 화면만 반복되지 않도록.
2. **항상 스트리밍 유지**: 이미지 분석용으로 지속적으로 프레임 제공.
3. **느림 개선**: 인코딩은 "프레임당 1번"으로 고정해 CPU 부하 감소.

### 3.1 권장: "공유 JPEG 1장" 방식 (구조 변경 최소)

- **한 곳에서만 인코딩**: 카메라 스레드(또는 전용 인코더 스레드 1개)가 `_latest_frame` → JPEG 바이트로 변환해 **공유 버퍼 1개**에만 씀.
- `/video_feed` 의 `generate()` 는 이 **이미 인코딩된 JPEG 바이트**를 그대로 읽어서 yield 만 함.
- 효과:
  - 접속자 수와 관계없이 **프레임당 인코딩 1번** → Pi에서 FPS·지연 개선.
  - 여러 클라이언트가 있어도 동일한 최신 프레임을 나눠 쓰므로, "멈춤" 현상 완화.
- 기존 API 유지: `/video_feed` (MJPEG), `/snapshot` 그대로 두고, AI 서버·브라우저 코드 변경 없이 적용 가능.

### 3.2 추가 개선 (선택)

- **클라이언트 끊김 감지**: `generate()` 내부에서 WSGI 환경의 클라이언트 연결 종료를 감지하면 루프를 빠져나와 스레드 해제. (구현 가능 범위에서 적용)
- **스트리밍 버퍼링 완화**: 사용하는 WSGI 서버에서 청크 단위 전송·버퍼 플러시 정책 확인.
- **카메라 오류 복구**: `read()` 연속 실패 시 재연결 또는 재시도 로직 추가해, `_latest_frame` 이 영원히 갱신 안 되는 상황 방지.

### 3.3 WebSocket 도입 여부

- **필수는 아님.** "공유 JPEG 1장"만으로도 멈춤·느림 대부분 해결 가능.
- WebSocket 장점:
  - 푸시 기반이라 브라우저와의 동기화가 명확함.
  - 연결 종료 감지가 쉬움.
- 단점:
  - AI 서버 `source_fetcher.py` 가 현재 **HTTP MJPEG 스트림**을 사용하므로, WebSocket만 쓰면 해당 부분 전부 수정 필요.
  - 브라우저는 `<img src="/video_feed">` 대신 JS로 WebSocket 수신 후 `<img>` 또는 `<canvas>` 에 그려야 함.
- 제안: **1단계는 공유 JPEG로 MJPEG 유지**, 동작 안정화 후 필요하면 WebSocket은 "브라우저 전용 보조 경로"로 추가 (예: `/ws/video`). AI 서버는 계속 `/video_feed` 또는 `/snapshot` 사용.

## 4. 진행 계획 (완료된 항목 반영)

| 단계 | 내용 | 비고 |
|------|------|------|
| **1** | **공유 JPEG 버퍼 도입** | ✅ 적용됨. 인코더 스레드 1개가 버퍼 갱신, `/video_feed`는 버퍼만 yield. |
| **2** | **클라이언트 끊김 감지** | ✅ GeneratorExit 처리로 루프 정상 종료. |
| **3** | **카메라 읽기 실패 시 처리** | ✅ 연속 실패 시 재연결. |
| **4** | **WebSocket 엔드포인트** | ✅ `/ws/video` 추가. AI 서버는 기존 HTTP 유지. |
