# DB Server 조사 보고서

## 📋 개요

DB Server는 음식 판매점(샌드위치 가게)의 주문 관리, 원재료 관리, 메뉴 레시피 관리를 위한 Flask 기반 REST API 서버입니다. PostgreSQL과 TimescaleDB를 활용하여 시계열 데이터를 효율적으로 관리하고, 실시간 대시보드와 웹 UI를 제공합니다.

## 💾 데이터베이스 구조

### 주요 테이블

#### 1. `store_order` - 주문 정보
- **주요 필드**:
  - `order_id` (UUID, PK): 주문 고유 ID
  - `channel`: 주문 채널 (online, offline 등)
  - `status`: 주문 상태 (placed, preparing, ready, completed, canceled, refunded)
  - `customer_name`, `customer_phone`: 고객 정보
  - `items` (JSONB): 주문 항목 목록
  - `total_amount`: 총 금액
  - `payment_status`: 결제 상태
  - `ordered_at`, `updated_at`: 타임스탬프

#### 2. `store_ingredient_mst` - 원재료 마스터
- **주요 필드**:
  - `ingredient_id` (UUID, PK)
  - `ingredient_sku` (UNIQUE): 원재료 SKU
  - `ingredient_name`: 원재료 이름
  - `category`: 카테고리 (bread, cheese, veg, meat, sauce, etc)
  - `base_unit`: 기본 단위 (g, ml 등)
  - `is_active`: 활성 상태

#### 3. `store_ingredient_txn` - 원재료 거래 이벤트
- **TimescaleDB Hypertable**: 시계열 데이터 최적화
- **주요 필드**:
  - `ingredient_txn_id` (UUID, PK)
  - `ingredient_sku`: 원재료 SKU (FK)
  - `qty_delta`: 수량 변동 (양수: 입고, 음수: 사용)
  - `txn_type`: 거래 유형 (in, out, waste, adjust)
  - `reason`: 거래 사유
  - `order_id`: 관련 주문 ID (FK)
  - `occurred_at`: 발생 시각 (PK, 타임스탬프)

#### 4. `store_menu_recipe_bom` - 메뉴 레시피 BOM
- **주요 필드**:
  - `menu_sku` (PK): 메뉴 SKU
  - `ingredient_sku` (PK, FK): 원재료 SKU
  - `qty_per_menu`: 메뉴당 원재료 사용량

### 예비 테이블

#### `store_inventory_txn` - 재고 거래 이벤트
- **상태**: 예비 테이블 (최소 기능만 제공)
- **용도**: 향후 확장을 위한 예비 테이블
- **제한사항**: 서비스 영역(대시보드, 분석)에서는 사용하지 않음

### Continuous Aggregates (선택사항)

TimescaleDB의 Continuous Aggregates를 활용한 사전 집계 뷰:

1. **`cagg_daily_inventory_change`**: 일별 원재료 재고 변동량 집계
2. **`cagg_daily_sales_qty`**: 일별 판매량 집계

> **참고**: Continuous Aggregates가 없어도 서버는 정상 작동하지만, 분석 API는 직접 계산하여 성능이 낮을 수 있습니다.

## 🔌 API 엔드포인트

### 헬스체크
- `GET /health`: 서버 상태 확인
- `GET /db/status`: TimescaleDB 상태 확인 (jobs, continuous aggregates 정보)

### 주문 관리 API
- `POST /orders`: 새 주문 생성
- `GET /orders`: 주문 목록 조회 (필터링: status, from, to, 페이징 지원)
- `GET /orders/<order_id>`: 주문 상세 조회
- `PATCH /orders/<order_id>/status`: 주문 상태 변경

**주문 상태 흐름**: `placed` → `preparing` → `ready` → `completed` (또는 `canceled`)

### 원재료 관리 API
- `GET /ingredients`: 원재료 목록 조회 (카테고리, 활성 상태 필터링)
- `GET /ingredients/<ingredient_sku>`: 원재료 상세 조회
- `POST /ingredients`: 원재료 생성
- `PATCH /ingredients/<ingredient_sku>`: 원재료 수정
- `DELETE /ingredients/<ingredient_sku>`: 원재료 삭제/비활성화
- `POST /ingredients/txn`: 원재료 거래 이벤트 생성 (입고/사용/폐기/조정)
- `GET /ingredients/txn`: 원재료 거래 이벤트 목록 조회

### 메뉴 레시피 API
- `GET /menu-recipe/<menu_sku>`: 메뉴 레시피 조회
- `POST /menu-recipe`: 메뉴 레시피 생성/업데이트
- `DELETE /menu-recipe/<menu_sku>`: 메뉴 레시피 전체 삭제
- `DELETE /menu-recipe/<menu_sku>/<ingredient_sku>`: 레시피 항목 삭제
- `GET /menu-recipe/list`: 모든 메뉴 레시피 목록 조회

### 분석 API
- `GET /analytics/daily/inventory-change`: 일별 재고 변동량 조회
- `GET /analytics/daily/sales`: 일별 판매량 조회
- `GET /analytics/top-sales`: TOP 판매 상품 조회

### 재고 API (예비)
- `POST /inventory/txn`: 재고 이벤트 생성 (예비 기능)
- `GET /inventory/txn`: 재고 이벤트 목록 조회

## ✨ 주요 특징

### 1. 트랜잭션 안전성
- 주문 상태 업데이트 시 `SELECT ... FOR UPDATE`를 사용하여 row-level locking
- 트랜잭션을 통한 안전한 상태 변경 보장
- 멱등성 보장 (다중 요청/재시도에도 안전)

### 2. Fallback 로직
- Continuous Aggregates 뷰가 없어도 API 정상 작동
- `store_order` 및 `store_ingredient_txn`에서 직접 계산
- 뷰가 있으면 성능 향상, 없어도 기능 정상 작동

### 3. 시계열 데이터 최적화
- TimescaleDB Hypertable을 활용한 효율적인 시계열 데이터 관리
- Continuous Aggregates를 통한 사전 집계로 분석 쿼리 성능 향상

### 4. 유연한 메타데이터 관리
- JSONB 필드를 활용한 확장 가능한 메타데이터 저장
- 스키마 변경 없이 추가 정보 저장 가능

## ⚠️ 제한사항 및 주의사항

### 1. 예비 테이블
- `store_inventory_txn`은 예비 테이블로 최소 기능만 제공
- 주문 완료 시 자동 재고 이벤트 생성 기능은 비활성화됨
- 필요시 `/inventory/txn` API를 직접 호출하여 수동으로 생성 가능

### 2. Continuous Aggregates
- 뷰가 없어도 동작하지만 성능은 낮을 수 있음
- 뷰 생성 및 권한 설정이 필요함 (스크립트 제공)

### 3. 인증/인가
- 현재 인증/인가 시스템이 없음
- 프로덕션 환경에서는 추가 보안 조치 필요

### 4. 로깅
- 기본 Flask 로깅만 사용
- 프로덕션 환경에서는 구조화된 로깅 시스템 권장

## 📊 데이터 흐름 예시

### 주문 생성 및 처리 흐름

1. **주문 생성** (`POST /orders`)
   - 주문 정보 저장 (`store_order`)
   - 상태: `placed`

2. **주문 준비 시작** (`PATCH /orders/<id>/status`)
   - 상태 변경: `placed` → `preparing`

3. **주문 완료** (`PATCH /orders/<id>/status`)
   - 상태 변경: `preparing` → `completed`
   - (참고: 자동 재고 이벤트 생성은 비활성화됨)

4. **원재료 사용 기록** (`POST /ingredients/txn`)
   - 원재료 거래 이벤트 생성 (`store_ingredient_txn`)
   - `qty_delta`: 음수 (사용량)
   - `txn_type`: `out`
   - `order_id`: 관련 주문 ID

### 분석 쿼리 흐름

1. **일별 판매량 조회** (`GET /analytics/daily/sales`)
   - Continuous Aggregate 뷰 (`cagg_daily_sales_qty`) 사용 (있는 경우)
   - 없으면 `store_order`에서 직접 집계

2. **일별 재고 변동량 조회** (`GET /analytics/daily/inventory-change`)
   - Continuous Aggregate 뷰 (`cagg_daily_inventory_change`) 사용 (있는 경우)
   - 없으면 `store_ingredient_txn`에서 직접 집계
