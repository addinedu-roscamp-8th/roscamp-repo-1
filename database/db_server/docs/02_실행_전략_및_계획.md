- **03**: **전체 API 테스트** 수행 → 결과 리포트, 실패 시 디버깅·완료 전략·계획 제시.

## 실행 전략

1. **기존 앱 유지**: store_* 기반 라우트/모델은 그대로 두고, **schema.sql 테이블용 모델·라우트를 추가**하여 두 스키마가 공존할 수 있게 합니다. (이후 schema.sql만 사용하도록 정리할지는 별도 결정)
2. **리소스 단위 CRUD**: menus, ingredients, recipes, recipe_steps, inventory, inventory_transactions, robots, orders, quality_check_results 각각에 대해 **Create·Read(목록/상세)·Update·Delete** 를 REST 규칙에 맞게 제공합니다.
3. **API 문서**: Flasgger 기존 사용 방식 유지. 모든 새 엔드포인트에 **Flasgger docstring**(요청/응답/에러)을 달아 `/api-docs` 에서 상세 명세가 보이도록 합니다. 필요 시 `apispec` 태그/설명 보강.
4. **테스트**: 새 CRUD API에 대해 **pytest**로 요청·응답·상태코드 검증. DB는 테스트 DB(test_sandwich_db) 또는 별도 테스트 DB에 **schema.sql 적용 후** 실행. 실패 시 원인별 수정 계획을 리포트에 포함합니다.

## 02 실행 계획 (CRUD API + API 문서)

| 단계 | 내용 | 산출물 |
|------|------|--------|
| 2.1 | **schema.sql용 SQLAlchemy 모델** 정의 (메뉴, 재료, 레시피, 레시피스텝, 재고, 재고거래, 로봇, 주문, 품질검사) | `app/models_kitchmatic.py` 또는 `app/models.py` 확장 |
| 2.2 | **CRUD Blueprint** 구현: 메뉴·재료·레시피·레시피스텝·재고·재고거래·로봇·주문·품질검사 각 리소스별 GET(목록/상세), POST(생성), PUT/PATCH(수정), DELETE. FK 있는 리소스는 관계 고려 (예: orders → menus, menu_id) | `app/routes/menus.py`, `ingredients_kitchmatic.py`, `recipes.py`, `inventory_kitchmatic.py`, `robots.py`, `orders_kitchmatic.py`, `quality_checks.py` 등 |
| 2.3 | 각 라우트에 **Flasgger docstring** (parameters, responses, examples) 작성. Swagger 태그 정리 (예: Menus (Kitchmatic), Orders (Kitchmatic)) | `/api-docs` 에서 확인 가능 |
| 2.4 | **create_app** 에 새 Blueprint 등록. 루트/health 엔드포인트에 새 API 경로 안내 추가 (선택) | `app/__init__.py`, 필요 시 `health.py` |

**API URL 설계 예시 (REST 관례)**

- `GET/POST /api/menus`, `GET/PUT/DELETE /api/menus/<id>`
- `GET/POST /api/ingredients`, `GET/PUT/DELETE /api/ingredients/<id>`
- `GET/POST /api/recipes`, `GET/PUT/DELETE /api/recipes/<id>`, `GET/POST /api/recipes/<id>/steps`
- `GET/POST /api/inventory`, `GET/PUT/DELETE /api/inventory/<id>`, `GET/POST /api/inventory/transactions`
- `GET/POST /api/robots`, `GET/PUT/DELETE /api/robots/<id>`
- `GET/POST /api/orders`, `GET/PATCH/DELETE /api/orders/<id>`
- `GET/POST /api/quality-check-results`, `GET/DELETE /api/quality-check-results/<id>`

(실제 prefix는 `/api` 또는 `/kitchmatic` 등으로 통일해 기존 `/orders` 와 구분 가능하게 함)

## 진행 여부 피드백 요청

- **01**은 위와 같이 조사·분석 리포트로 반영했습니다.
- **02**는 위 계획대로 schema.sql 기준 CRUD API 추가 + api docs 상세 명세를 진행할 예정입니다.
- **03**은 02 완료 후 동일 서버 기준으로 테스트 작성·실행·리포트까지 진행할 예정입니다.

**확인 요청:**

1. **API URL prefix**: schema.sql 기반 API를 `/api` 아래에 둘까요? (예: `/api/menus`, `/api/orders`) 아니면 `/kitchmatic/menus` 처럼 다른 prefix를 원하시나요?
2. **기존 store_* API**: 그대로 유지할까요, 아니면 이번 작업에서 비활성화(주석 처리)해도 될까요?
3. **테스트 DB**: 이미 schema.sql을 적용한 별도 DB(예: `kitchmatic_test`)를 사용할 계획이 있나요? 없다면 `test_sandwich_db`에 schema.sql 테이블을 추가하는 방식으로 진행해도 될까요?

위 세 가지에 대한 답을 알려주시면, 그에 맞춰 02·03 구현을 진행하겠습니다. 답이 없어도 기본값으로 **prefix `/api`**, **기존 store_* 유지**, **test_sandwich_db에 schema.sql 테이블 존재 가정**으로 진행할 수 있습니다.
