FMS는 전체 시스템의 두뇌 역할을 합니다. 총 10,225 라인의 코드로 구성되어 있으며, 가장 큰 fms_node.py가 2,361 라인입니다. 충돌 회피 모듈이 1,297 라인으로 두 번째로 큰데, 이는 다중 로봇 환경에서 충돌 방지가 얼마나 복잡한지를 보여줍니다. 설계 원칙으로는 Clean Architecture를 적용하여 Domain, Application, Infrastructure 레이어를 분리했고, SOLID 원칙, 특히 Dependency Inversion을 적극 활용했습니다.

주문 상태 머신 (Order State Machine)

┌─────────────┐ │ RECEIVED │ ← 주문 접수 └──────┬──────┘ │ send_cooking_command() │ navigate_robot('point13') ▼ ┌─────────────┐ │ COOKING │ ← 로봇팔 조리 중, pinky가 point13으로 이동 └──────┬──────┘ │ robot arrives at point13 ▼ ┌─────────────┐ ┌─────────────────────────────────────────┐ │ LOADING │ ←───────│ 문제: 로봇이 point13에 도착했지만 │ └──────┬──────┘ │ 조리가 안 끝났을 때 대기 필요 │ │ cooking_complete│ 해결: 조리 완료 이벤트 기반 전환 │ ▼ └─────────────────────────────────────────┘ ┌─────────────┐ │ LOADED │ ← 음식 적재 완료 └──────┬──────┘ │ navigate_robot('tableN') ▼ ┌─────────────┐ │ DELIVERING │ ← 테이블로 이동 중 └──────┬──────┘ │ robot arrives at table ▼ ┌─────────────┐ │ ARRIVED │ ← 고객에게 알림 발송 └──────┬──────┘ │ delivery_complete from GUI ▼ ┌─────────────┐ │ COMPLETED │ ← 주기 완료, 주차장으로 복귀 └─────────────┘
주문 상태 머신입니다. 주문이 접수되면 RECEIVED 상태에서 시작합니다. 동시에 로봇팔에 조리 명령을 보내고, 서빙 로봇은 픽업 포인트로 이동합니다. 여기서 중요한 문제가 발생했습니다. 로봇이 픽업 포인트에 먼저 도착했는데 조리가 안 끝났을 때, 단순히 타이머로 기다리면 조리 시간이 가변적이라 문제가 됩니다. 해결책은 이벤트 기반 전환입니다. 조리 완료 토픽을 구독하고, 두 조건이 모두 충족될 때만 다음 단계로 넘어갑니다.

통신 아키텍처입니다. 세 가지 통신 방식을 사용합니다. 첫째, GUI와 FMS는 TCP/JSON으로 통신합니다. Customer GUI는 포트 9000, Admin GUI는 포트 9999를 사용합니다. 둘째, FMS와 로봇은 ROS2/DDS로 통신합니다. 각 로봇이 다른 Domain ID를 사용하여 격리됩니다. Domain Bridge가 FMS(Domain 25)와 각 로봇을 연결합니다. 셋째, AI Server와는 REST API로 통신합니다.

8. 문제 해결 사례 ①

DDS Discovery 실패 문제

🚨 문제 상황
  • SSH는 되는데 ROS2 토픽이 안 보임
  • ros2 topic list 결과가 비어있음
  • 로봇은 정상 동작 중

🔍 원인 분석
  • ROS2 기본: Multicast UDP 사용
  • WiFi 공유기가 Multicast 차단
  • 노드 간 Discovery 불가능
✅ 해결책: Unicast Discovery
# cyclonedds_main.xml <Peers> <Peer address="192.168.1.7"/> <Peer address="192.168.1.6"/> <Peer address="192.168.1.11"/> </Peers> # 환경변수 설정 export RMW_IMPLEMENTATION= rmw_cyclonedds_cpp export CYCLONEDDS_URI=file:// cyclonedds_main.xml

📈 결과
  • Peer IP 직접 지정으로 안정적 통신
  • WiFi 환경에서도 100% 연결 성공
첫 번째 문제 해결 사례입니다. 문제는 SSH로 로봇에 접속은 되는데, ROS2 토픽이 전혀 보이지 않는 것이었습니다. 로봇에서 ros2 topic list를 하면 토픽이 보이는데, Master PC에서는 아무것도 안 보였습니다. 원인을 분석해보니, ROS2가 기본으로 Multicast UDP를 사용하는데, WiFi 공유기가 Multicast 패킷을 차단하고 있었습니다. 해결책은 CycloneDDS의 Unicast Discovery 기능을 사용하는 것입니다. 각 노드가 연결할 Peer IP를 XML 설정 파일에 명시적으로 지정합니다. 이렇게 하면 Multicast 없이도 노드 간 Discovery가 가능합니다.

문제 해결 사례 ②

Multi-Domain 토픽 충돌 문제

🚨 문제 상황
  • 로봇 3대가 같은 토픽명 사용
  • /cmd_vel 명령이 모든 로봇에 전달
  • 개별 제어 불가능

🔍 원인 분석
  • 동일 Domain에서 동일 토픽명 충돌
  • Namespace만으로는 불충분
  • Nav2 Action도 충돌
✅ 해결책: Multi-Domain + Bridge
# Domain 할당 FMS: Domain 25 pinky1: Domain 11 pinky2: Domain 12 pinky3: Domain 13 # domain_bridge.yaml from_domain: 11 to_domain: 25 topics: - topic: /pinky1/amcl_pose type: geometry_msgs/msg/ PoseWithCovarianceStamped

📈 결과
  • 로봇별 완전 격리

  • 충돌 0건
두 번째 문제 해결 사례입니다. 문제는 로봇 3대가 모두 같은 토픽명을 사용해서 충돌이 발생한 것입니다. /cmd_vel 명령을 보내면 3대가 모두 같은 방향으로 움직였습니다. Namespace로 /pinky1/cmd_vel, /pinky2/cmd_vel로 분리해도, 같은 Domain에 있으면 여전히 문제가 있었습니다. 특히 Nav2 Action Server가 충돌했습니다. 해결책은 Multi-Domain 아키텍처입니다. 각 로봇에 별도의 Domain ID를 부여하여 완전히 격리합니다. 그리고 domain_bridge 패키지로 필요한 토픽만 선택적으로 연결합니다.

문제 해결 사례 ③

로봇-조리 상태 동기화 문제

🚨 문제 상황
  • 로봇이 픽업 포인트 도착
  • 조리가 아직 안 끝남
  • 언제 출발해야 하나?

❌ 실패한 시도
  • 고정 타이머 (30초 대기)
  • → 조리 시간이 가변적이라 실패
  • 폴링 방식
  • → 지연 발생, 리소스 낭비
✅ 해결책: Event-Driven + 조건부 전환
# order_handler.py def check_can_proceed_to_delivery(): robot_at_pickup = robot_state == AT_POINT13 cooking_done = loading_complete_received if robot_at_pickup and cooking_done: transition_to(DELIVERING) navigate_robot(table_position)

📐 설계 원칙
  • 이벤트 기반 상태 전환
  • 두 조건 AND 충족 시만 진행
  • Callback 등록으로 느슨한 결합
세 번째 문제입니다. 로봇이 픽업 포인트에 도착했는데 음식이 아직 준비 안 됐을 때, 언제 출발해야 하는지의 문제입니다. 처음에는 고정 타이머로 30초 대기했는데, 메뉴마다 조리 시간이 달라서 실패했습니다. 폴링 방식도 시도했는데, 지연이 발생하고 리소스 낭비였습니다. 최종 해결책은 이벤트 기반 설계입니다. 로봇 도착과 조리 완료, 두 이벤트를 모두 수신하고, 두 조건이 AND로 충족될 때만 다음 단계로 전환합니다. 어느 쪽이 먼저 완료되든 상관없이 정확하게 동기화됩니다.

Robot Error │ ▼ ErrorDetector (0.5Hz 모니터링) │ │ /fms/error_alert 발행 ▼ Main Server │ │ TCP broadcast ▼ Admin GUI (팝업 알림) │ │ 운영자 선택 ▼ ┌────────┬────────┬────────┐ │ RETRY │ RETURN │ STOP │ │ 재시도 │ 복귀 │ 정지 │ └────────┴────────┴────────┘
네 번째는 오류 대응 시스템입니다. 서빙 중 발생할 수 있는 오류 유형을 정의했습니다. 네비게이션 실패, 통신 끊김, 배터리 부족, 작업 타임아웃, 장애물 감지 등입니다. ErrorDetector가 0.5Hz로 모니터링하다가 오류를 감지하면, /fms/error_alert 토픽을 발행합니다. Main Server가 이를 TCP로 Admin GUI에 전달하고, 관리자에게 팝업 알림을 띄웁니다. 관리자는 상황에 맞게 재시도, 복귀, 정지 중 하나를 선택합니다.

⚡ Skip Mode

목적
  • 실제 로봇/로봇팔 없이 테스트
  • 외부 의존성 제거
  • 빠른 개발 사이클
동작 방식
  • Precision parking: 2초 Mock
  • Food loading: 3초 Mock
  • 상태 전환은 실제와 동일
# Skip Mode 실행 ros2 run fms fms_node \ --ros-args \ -p skip_robot_arm:=true \ -p skip_precision:=true
테스트 전략입니다. 총 155개 테스트를 작성했습니다. Unit 테스트 80개, Integration 테스트 35개, E2E 테스트 40개입니다. 핵심은 Skip Mode입니다. 실제 로봇이나 로봇팔 없이도 전체 시스템을 테스트할 수 있습니다. Precision parking은 2초 후 완료로 Mock하고, Food loading은 3초 후 완료로 Mock합니다. 상태 전환 로직은 실제와 완전히 동일하게 동작합니다. 이를 통해 개발 중에도 빠르게 E2E 테스트를 돌릴 수 있었습니다.

10. 데모 시나리오

1. 주문 접수
고객이 키오스크에서 "햄치즈샌드위치 2개" 음성 주문
2. 조리 시작
FMS가 Robot Arm에 조리 명령 전송, pinky1 픽업 포인트로 출발
3. 품질 검수
AI Server가 YOLO로 샌드위치 검수, 정상 판정
4. 음식 적재
pinky1 도착, 로봇팔이 샌드위치를 로봇에 적재
5. 테이블 서빙
pinky1이 테이블 1로 이동, Nav2 네비게이션
6. 도착 알림
키오스크에 푸시 알림, "음식이 도착했습니다"
7. 수령 완료
고객이 수령 버튼 클릭, pinky1 주차장 복귀

전체 소요시간: 약 3-5분
데모 시나리오입니다. 고객이 키오스크에서 음성으로 주문합니다. "햄치즈샌드위치 2개 주세요" FMS가 주문을 받아서 로봇팔에 조리 명령을 보내고, 동시에 가용 가능한 서빙 로봇을 픽업 포인트로 보냅니다. 로봇팔이 샌드위치를 조립하면, AI 서버가 YOLO로 품질을 검수합니다. 정상이면 로봇팔이 서빙 로봇에 음식을 적재합니다. 서빙 로봇은 Nav2로 테이블까지 자율 주행합니다. 도착하면 키오스크에 푸시 알림이 갑니다. 고객이 수령 완료 버튼을 누르면 로봇이 주차장으로 복귀합니다. 전체 소요시간은 약 3-5분입니다.

11. 배운 점 / 교훈

✅ 잘한 점

  • Multi-Domain 아키텍처
    로봇 격리로 충돌 문제 해결
  • Skip Mode 도입
    개발 속도 3배 향상
  • Event-Driven 설계
    상태 동기화 문제 해결
  • Unicast DDS 설정
    WiFi 환경 안정화

📚 개선 포인트

  • 초기 아키텍처 설계
    Multi-Domain을 처음부터 고려했으면...
  • 네트워크 환경 테스트
    실제 WiFi 환경에서 조기 테스트 필요
  • 에러 복구 자동화
    현재 수동 개입 필요, 자동화 여지
  • 부하 테스트
    100+ 동시 주문 시나리오 미검증
배운 점과 교훈입니다. 잘한 점은, Multi-Domain 아키텍처를 도입해서 로봇 간 충돌을 완전히 해결한 것입니다. Skip Mode 덕분에 실제 로봇 없이도 개발과 테스트가 가능했습니다. Event-Driven 설계로 로봇과 조리 상태 동기화 문제를 우아하게 해결했습니다. 개선 포인트로는, Multi-Domain을 프로젝트 초기부터 고려했으면 좋았을 것입니다. 중간에 아키텍처를 변경하느라 시간이 많이 소요되었습니다. 그리고 WiFi 환경에서의 DDS 문제를 더 일찍 발견했으면 좋았습니다. 실제 환경에서 조기 테스트의 중요성을 느꼈습니다.
