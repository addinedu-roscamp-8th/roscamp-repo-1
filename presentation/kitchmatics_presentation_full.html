🔗 ROS2 Multi-Domain 설계

Domain ID Component IP Address 역할
25 FMS (Master) 192.168.1.3 중앙 관제, Domain Bridge
11 pinky1 192.168.1.7 서빙 로봇 #1
12 pinky2 192.168.1.6 서빙 로봇 #2
13 pinky3 192.168.1.11 서빙 로봇 #3
20 Robot Arms 192.168.1.4 조리 로봇팔
Why Multi-Domain? 각 로봇이 동일한 토픽명(/cmd_vel, /odom)을 사용하므로 Domain으로 분리
5개의 Domain ID를 사용합니다. 각 로봇이 독립적인 Domain에서 동작하고, Domain Bridge로 연결합니다.

🌉 Domain Bridge 구조

Domain 11 (pinky1) Domain 25 (FMS) Domain 12 (pinky2) /cmd_vel ─────► /pinky1/cmd_vel /odom ─────► /pinky1/odom /amcl_pose ─────► /pinky1/amcl_pose │ │ Domain Bridge │ │ /pinky2/cmd_vel ◄───── /cmd_vel /pinky2/odom ◄───── /odom /pinky2/amcl_pose ◄───── /amcl_pose
# domain_bridge.yaml - topic: /cmd_vel from_domain: 25 to_domain: 11 remap: /pinky1/cmd_vel → /cmd_vel
Domain Bridge가 토픽을 리매핑합니다. FMS에서는 /pinky1/cmd_vel로 명령하면, pinky1에서는 /cmd_vel로 수신됩니다.

📦 FMS Node 구조

class FMSNode(Node): def __init__(self): # Application Layer self.order_handler = OrderHandler() self.fleet_controller = FleetController() self.error_detector = ErrorDetector() # Infrastructure Layer self.gui_server = GUITCPServer(port=9000) # ROS2 Communication self.nav_clients = {} # Robot navigation action clients self.cooking_pub = self.create_publisher(CookingOrder, '/cooking/order') # Register callbacks (Dependency Injection) self.order_handler.register_callbacks( send_cooking_command=self._send_cooking_command, navigate_robot=self._navigate_robot, send_gui_notification=self._send_gui_notification )
FMS Node는 Dependency Injection 패턴을 사용합니다. Application Layer가 Infrastructure에 직접 의존하지 않습니다.

📋 Order Handler

책임

  • 주문 Workflow 관리
  • 상태 전이 제어
  • 콜백 트리거

상태 전이

RECEIVED → COOKING → LOADING
→ LOADED → DELIVERING
→ ARRIVED → COMPLETED
class OrderHandler: def handle_new_order(self, order): workflow = OrderWorkflow(order) # 조리 명령 workflow.transition_to(COOKING) self.send_cooking_command(order) # 로봇 배차 robot = self.fleet.get_available() self.navigate_robot(robot, 'kitchen') def handle_cooking_complete(self, order_id): workflow = self.get_workflow(order_id) if workflow.robot_at_kitchen: workflow.transition_to(LOADED) self.navigate_robot(robot, 'table')
Order Handler는 주문의 전체 생명주기를 관리합니다. 조리 완료와 로봇 도착을 동기화합니다.

def get_available_robot(self): # 우선순위: IDLE > 거리순 idle_robots = [r for r in self.robots if r.status == IDLE] if not idle_robots: return None # 주방과 가장 가까운 로봇 return min(idle_robots, key=lambda r: r.distance_to('kitchen'))
Fleet Controller가 로봇 배차를 담당합니다. IDLE 상태의 로봇 중 주방과 가장 가까운 로봇을 선택합니다.

🔄 Order State Machine

┌─────────────┐ │ RECEIVED │ ← 주문 접수 └──────┬──────┘ │ send_cooking_command() │ navigate_robot('kitchen') ▼ ┌─────────────┐ │ COOKING │ ← 조리 중 + 로봇 이동 중 └──────┬──────┘ │ robot_arrived_kitchen() ▼ ┌─────────────┐ │ LOADING │ ← 조리 완료 대기 └──────┬──────┘ │ cooking_complete() AND robot_at_kitchen ▼ ┌─────────────┐ │ LOADED │ ← 적재 완료 └──────┬──────┘ │ navigate_robot('table') ▼ ┌─────────────┐ │ DELIVERING │ ← 테이블로 이동 중 └──────┬──────┘ │ robot_arrived_table() │ send_gui_notification() ▼ ┌─────────────┐ │ ARRIVED │ ← 도착, 고객 확인 대기 └──────┬──────┘ │ delivery_confirmed() ▼ ┌─────────────┐ │ COMPLETED │ ← 완료 └─────────────┘
주문 상태 머신입니다. 각 상태 전이마다 특정 조건과 액션이 정의되어 있습니다.

⚠️ Error Detector

감지 항목

  • Navigation Timeout: 목적지 미도착
  • Robot Stuck: 이동 중 정지
  • Communication Loss: 통신 두절
  • Cooking Timeout: 조리 지연

복구 옵션

  • RETRY 동일 작업 재시도
  • SKIP 다음 단계로 진행
  • MANUAL 운영자 개입 요청
class ErrorDetector: def check_navigation_timeout(self, robot_id, timeout=60): elapsed = time.time() - self.nav_start_time[robot_id] if elapsed > timeout: return ErrorEvent(type=NAV_TIMEOUT, robot=robot_id, options=[RETRY, SKIP, MANUAL])
Error Detector가 다양한 에러 상황을 감지하고, 복구 옵션을 제시합니다.

Part 5

Problems & Solutions

문제 해결 사례

Problem #1: DDS Discovery 실패

증상

  • Master PC에서 ros2 topic list 실행
  • 로봇의 토픽이 전혀 보이지 않음
  • SSH 연결은 정상 동작
  • ping도 성공
$ ros2 topic list /parameter_events /rosout # 로봇 토픽 없음! $ ping 192.168.1.7 64 bytes from 192.168.1.7: icmp_seq=1 ttl=64 time=2.34 ms # ping은 성공
첫 번째 문제입니다. 로봇과 네트워크는 연결되어 있는데, ROS2 토픽이 보이지 않았습니다.

Problem #1: 조사 과정

디버깅 단계

1. 로봇에서 직접 확인

SSH로 접속해서 ros2 topic list → 로컬에서는 토픽 정상

2. Domain ID 확인

양쪽 모두 같은 Domain ID 사용 확인

3. Wireshark 패킷 분석

Multicast 패킷이 수신되지 않음!

4. Router 설정 확인

WiFi AP에서 Multicast 차단 발견

단계별로 조사했습니다. 로봇 자체는 정상이었고, 네트워크 레벨에서 문제를 발견했습니다.

Problem #1: 근본 원인

ROS2 DDS 기본 동작

  • 노드 발견에 Multicast UDP 사용
  • 주소: 239.255.0.1
  • 포트: 7400-7500
문제: 대부분의 WiFi AP는 보안/성능상 Multicast를 차단하거나 제한
[Master PC] [WiFi AP] [Robot] │ │ │ │ Multicast UDP │ │ │ 239.255.0.1:7400 │ │ │───────────────────────►│ ✗ │ │ │ (Blocked) │ │ │ │ │ No Discovery! │ │ │◄ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─│ │
근본 원인은 WiFi AP의 Multicast 차단이었습니다. 많은 공유기들이 기본적으로 이 설정을 가지고 있습니다.

Solution #1: Unicast Discovery

해결 접근 방식

Option 1: Router 설정 변경
  • Multicast 허용
  • ❌ 모든 환경에서 불가능
  • ❌ 보안 우려
Option 2: Unicast Discovery ✓
  • 직접 IP 주소로 통신
  • ✅ 모든 WiFi에서 동작
  • ✅ CycloneDDS 지원
선택: CycloneDDS의 Unicast Peer Discovery 사용
두 가지 옵션을 검토했고, Unicast Discovery가 더 범용적인 해결책이었습니다.

Solution #1: 구현

CycloneDDS 설정 파일

<!-- cyclonedds_main.xml (Master PC) --> <CycloneDDS> <Domain> <General> <NetworkInterfaceAddress>192.168.1.3</NetworkInterfaceAddress> </General> <Discovery> <ParticipantIndex>auto</ParticipantIndex> <Peers> <Peer address="192.168.1.7"/> <!-- pinky1 --> <Peer address="192.168.1.6"/> <!-- pinky2 --> <Peer address="192.168.1.11"/> <!-- pinky3 --> </Peers> </Discovery> </Domain> </CycloneDDS>
# 환경 변수 설정 export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp export CYCLONEDDS_URI=file:///path/to/cyclonedds_main.xml
CycloneDDS XML 파일에 Peer IP 주소를 명시합니다. 환경 변수로 DDS 구현체를 지정합니다.

Problem #2: Topic Name Collision

증상

  • 모든 로봇이 같은 토픽명 사용: /cmd_vel, /odom
  • 한 도메인에서 3대 로봇 운영 시 데이터 혼선
  • 어떤 /amcl_pose가 어떤 로봇인지 구분 불가
$ ros2 topic list /cmd_vel # pinky1? pinky2? pinky3? /odom # 어떤 로봇의 odometry? /amcl_pose # 위치 데이터 혼합! /scan # LiDAR 데이터 충돌
두 번째 문제입니다. TurtleBot3의 기본 토픽명이 모두 동일해서 구분이 불가능했습니다.

Problem #2: 영향

운영상 문제

  • ❌ 잘못된 로봇에 명령 전달
  • ❌ 위치 추정 오류
  • ❌ 충돌 위험
  • ❌ Fleet 관리 불가능

기술적 한계

  • ❌ TurtleBot3 펌웨어 수정 어려움
  • ❌ Nav2 내부 토픽명 하드코딩
  • ❌ 단순 remapping으로 해결 불가
FMS: "pinky1, go to kitchen!" │ │ Publish /cmd_vel ▼ ┌────────┬────────┬────────┐ │pinky1 │pinky2 │pinky3 │ ← 3대 모두 같은 토픽 구독! │ ✓? │ ✓? │ ✓? │ └────────┴────────┴────────┘

Problem #3: 조리-로봇 동기화

증상

Case A: 로봇 먼저 도착
  • 로봇이 주방에 도착
  • 음식 아직 조리 중
  • 로봇 대기 → 효율 저하
Case B: 음식 먼저 완성
  • 조리 완료
  • 로봇 아직 이동 중
  • 음식 방치 → 품질 저하
Timeline: Robot: ────[Moving]────────────●(Arrived)────[Waiting...]──── Cooking: ────────────[Cooking]─────────────────●(Complete)──── ↑ Race Condition!
세 번째 문제입니다. 로봇 도착과 조리 완료 시점이 일치하지 않아 비효율이 발생했습니다.

Problem #3: 분석

실패한 접근 방식

Approach 1: 타이머 기반
# 조리 시작 후 30초 대기 time.sleep(30) navigate_robot('kitchen')

❌ 조리 시간 가변적

❌ 로봇 이동 시간 가변적

Approach 2: 폴링
while True: if is_cooking_done(): navigate_robot('kitchen') break time.sleep(1)

❌ CPU 낭비

❌ 반응 지연

타이머와 폴링 방식 모두 시도했지만 효과적이지 않았습니다.

Solution #3: Event-Driven State Machine

설계 원칙

핵심: 조리 완료와 로봇 도착을 독립적 이벤트로 처리, AND 조건으로 다음 단계 진행
class OrderWorkflow: def __init__(self): self.cooking_complete = False self.robot_at_kitchen = False def on_cooking_complete(self): self.cooking_complete = True self._check_loading_ready() def on_robot_arrived_kitchen(self): self.robot_at_kitchen = True self._check_loading_ready() def _check_loading_ready(self): # AND 조건: 둘 다 만족해야 다음 단계 if self.cooking_complete and self.robot_at_kitchen: self.transition_to(LOADED) self.navigate_robot('table')
Event-Driven 방식으로 변경했습니다. 두 이벤트가 모두 발생해야 다음 단계로 진행합니다.

Solution #3: 상태 다이어그램

┌─────────────┐ │ COOKING │ └──────┬──────┘ │ ┌─────────────┼─────────────┐ │ │ │ ▼ │ ▼ ┌────────────────┐ │ ┌────────────────┐ │ Robot Arrived │ │ │ Cooking Done │ │ (Event A) │ │ │ (Event B) │ └────────┬───────┘ │ └────────┬───────┘ │ │ │ │ Wait for Both │ │ │ │ └─────────────┼─────────────┘ │ ┌──────▼──────┐ │ A AND B │ │ Satisfied │ └──────┬──────┘ │ ┌──────▼──────┐ │ LOADED │ └─────────────┘
두 이벤트가 어떤 순서로 발생하든, 둘 다 만족되면 LOADED 상태로 전이합니다.

Solution #4: TCP/JSON Protocol

프로토콜 설계

# 메시지 포맷 ┌──────────────┬─────────────────────────────────┐ │ Length (4B) │ JSON Payload │ │ Big-endian │ UTF-8 encoded │ └──────────────┴─────────────────────────────────┘ # GUI → FMS: 주문 { "command": "new_order", "table_number": 1, "order": { "items": [{"menu_id": 1, "name": "햄버거", "quantity": 2}] } } # FMS → GUI: 도착 알림 (Push) { "type": "delivery_notification", "data": { "order_id": "ORD-001", "table_number": 1, "message": "음식이 도착했습니다!" } }
4바이트 길이 헤더 + JSON 페이로드 구조로 설계했습니다. 간단하면서도 확장 가능합니다.

Solution #4: 서버 구현

class GUITCPServer: def __init__(self, port=9000): self.clients = [] # Connected clients self.handlers = {} # Message handlers def register_handler(self, command, handler): """핸들러 등록 (Open/Closed Principle)""" self.handlers[command] = handler def broadcast(self, message): """모든 클라이언트에 Push 알림""" data = json.dumps(message).encode('utf-8') header = struct.pack('>I', len(data)) for client in self.clients: client.send(header + data) def _handle_client(self, client_socket): """클라이언트별 스레드에서 실행""" while True: header = client_socket.recv(4) length = struct.unpack('>I', header)[0] data = client_socket.recv(length) message = json.loads(data.decode('utf-8')) handler = self.handlers.get(message['command']) if handler: handler(message)
Thread-per-client 모델로 구현했습니다. broadcast로 Push 알림을 보냅니다.

🧪 Skip Mode 아키텍처

문제: 물리적 로봇 없이 FMS 로직을 테스트해야 함
class FMSNode: def __init__(self): self.skip_mode = self.get_parameter('skip_mode').value def navigate_robot(self, robot_id, waypoint): if self.skip_mode: # 시뮬레이션: 3초 후 도착으로 처리 self.get_logger().info(f"[SKIP] {robot_id} → {waypoint}") self.create_timer(3.0, lambda: self._on_nav_complete(robot_id)) else: # 실제 Navigation Action 호출 self._send_nav_goal(robot_id, waypoint)
사용: ros2 run fms fms_node --ros-args -p skip_mode:=true
Skip Mode는 물리적 로봇 없이 FMS 로직을 테스트할 수 있게 해줍니다.
